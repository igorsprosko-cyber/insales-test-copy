# 3. ВАЖНЫЕ УРОКИ

## JS вместо CSS

Category-card инцидент доказал: не лечить CSS/Liquid через JS с `!important`.

## Не путать доказательство и гипотезу

`tag.js`, MutationObserver, изображения, CSS, fonts и third-party должны связываться с конкретным trace/network evidence. Само наличие ресурса ещё не доказывает его причинность.

## Не путать network time и CPU time

`common.v2.27.9.js` может находиться десятки секунд в передаче при плохой сети, не выполняясь десятки секунд на CPU.

## Не смешивать PageSpeed runs

Desktop и mobile, разные throttling conditions и разные запуски нельзя объединять в один «до/после» показатель без явной маркировки.

## Audit discipline

Правильный цикл: **доказательство → маленькая группа изменений → повторный тест → diff → runtime QA**.

# 16. FINAL PRINCIPLE

**Не оптимизировать ради цифры PageSpeed. Оптимизировать подтверждённую причину, не ломая рабочий сайт.**

Каждое следующее performance-изменение должно быть связано с:

`finding → evidence → minimal code change → PageSpeed → Network → Performance → visual QA → Git diff → ИСТОРИЯ_РАБОТ.md`.
ЗАКОН АРХИТЕКТУРЫ ЗАГРУЗКИ И ПОСТРОЕНИЯ КОДА

Critical Path → First Paint/LCP → Interaction → Analytics/Third-party → Background

Сначала HTML, критический CSS, H1/основной контент, LCP и минимально необходимая функциональность.
LCP должен обнаруживаться максимально рано из первоначального HTML; не lazy-load; при необходимости использовать корректный fetchpriority.
После первого экрана — функциональный JS взаимодействия.
Google Analytics, Яндекс Метрика, GTM, SmartCaptcha и прочий third-party не считать критическими зависимостями без доказанной необходимости.
Аналитика не должна блокировать HTML parser, FCP/LCP или конкурировать с критическими ресурсами за сеть и CPU.
Использовать async, defer, conditional/lazy initialization и другие безопасные механизмы отложенного запуска.
Второстепенные виджеты, эффекты, изображения и фоновые задачи — после critical path или по необходимости.
Не допускать чрезмерного количества одновременно высокоприоритетных ресурсов.
Не «переносить Метрику вниз» механически — сохранить корректность аналитики, но убрать её из критического пути.
Каждый performance/refactor: baseline → маленькое изменение → PageSpeed/Trace → diff → runtime/visual QA.
Массовый refactor запрещён без доказанной причинности.
PageSpeed рассматривается не как список отдельных исправлений, а как диагностика архитектуры загрузки.
Приоритеты определяются реальным waterfall/trace, а не предположением.
SEO, Accessibility и Agentic Browsing нельзя улучшать ценой производительности и наоборот.
Защищённую бизнес-логику калькулятора и Metal Routing не менять в рамках performance-архитектуры.
