## 3. ПРАВИЛА ПРОЕКТА — ГДЕ ЛЕЖАТ И ЧТО ГЛАСЯТ

`REVIEW_SCOPE.md`, `PR5_AUDIT_NOTES.md`. Прочитать их перед началом

### Главные правила (кратко):

- **Стиль**: промышленный минимализм, чёрный/белый, только Montserrat
  (текст) + Playfair Display (заголовки), сетка отступов 4px, тонкие
  чёрные рамки, акцент `#5E8C31` только для hover/ссылок/успеха.
- **Рабочий цикл**: ПРОЧИТАНО → ПРОАНАЛИЗИРОВАНО → ИЗМЕНЕНО → ПЕРЕЧИТАНО
  → ПРОВЕРЕНО → DIFF. Никогда не выдумывать содержимое файлов/результаты.
- **Только точечные правки.** Не рефакторить, не менять архитектуру, не
  добавлять библиотеки без явного задания.
- **`V2.1_HOME_APPEND.liquid`** — защищённый эталон главной страницы. Не
  переделывать его ради стандартизации остальных страниц. Если находится
  реальный конфликт — сначала сообщить, не менять самостоятельно.
- **Калькулятор — АБСОЛЮТНЫЙ ЗАПРЕТ.** Никогда не менять:
  `calcWood()`, `handleWoodHeight()`, `handleWoodShape()`,
  `handleWoodForm()`, `handleWoodDim()`, `handleWoodTilt()`,
  `handleWoodBase()`, `handleWoodColor()`, `openManagerForm()`,
  `fillComment()`, любые `wood-*`/`panel-wood`/`panel-metal` ID, а также
  цены, НДС, скидки, вес, объём заказа, любую бизнес-логику.
  **Metal Routing** (то, что кнопка металла в калькуляторе использует
  дерево-поля через `openManagerForm('metal')`) — это **НЕ баг**, а
  незавершённая функция. Не чинить, не помечать как дефект.

## 4. ПРОТОКОЛ ФАКТИЧЕСКОГО ПОДТВЕРЖДЕНИЯ (обязателен для всех ИИ)

Правило появилось из-за инцидента с Qwen Coder (см. раздел 6) и с тех пор
действует для Claude, ChatGPT и любого другого исполнителя:

- **НЕТ ВНЕШНЕГО ДОКАЗАТЕЛЬСТВА → НЕТ ВЫПОЛНЕННОГО ДЕЙСТВИЯ.**
- Запрещены слова «готово/исправлено/сохранено/проверил» без реального
  доказательства.
- Каждое изменение файла: BEFORE (реальный SHA/содержимое) → CHANGE
  (реальная запись) → AFTER (новый SHA) → COMMIT (commit SHA) → VERIFY
  (повторное чтение — **обязательно свежим независимым `git clone`, не
  из локального кэша**) → DIFF (фактический diff).
- Только три статуса: **VERIFIED** / **PARTIALLY VERIFIED** /
  **NOT VERIFIED**. Если нет доказательства — писать `NOT VERIFIED`, не
  гадать.
- Если операция физически невозможна — писать `WRITE NOT AVAILABLE` /
  `READ FAILED` / `RUNTIME NOT AVAILABLE`, не симулировать успех.
- **После каждого push — заново клонировать репозиторий с нуля** (не
  доверять локальному рабочему каталогу) и напрямую прочитать
  содержимое файла/коммита с GitHub, прежде чем писать «VERIFIED».

## 6. ИНЦИДЕНТ С QWEN CODER — ПОЧЕМУ ОН НА ПАУЗЕ

Два отдельных случая, оба обнаружены независимой проверкой Claude (не на
слово):

1. **Несанкционированный рефакторинг.** Qwen переписал весь `theme.scss`
   без задания — удалил поддержку редактора InSales (`.outside-widgets`,
   `.delete-widget-link` и т.д.), удалил `@import "settings"`, добавил
   глобальный CSS-reset. Это прямое нарушение правила «не рефакторить
   без задания». Ветка была отброшена, работа восстановлена с нуля от
   эталона.

2. **Фабрикация отчёта.** В задаче, где Qwen явно запретили менять
   что-либо (только читать и подтверждать факты), он всё равно выдал
   ложный «VERIFIED»-отчёт: перепутал значение `object-fit` на
   противоположное, придумал несуществующую структуру папок
   (`templates/`, `snippets/`, `assets/` — которых нет в этом
   InSales-репозитории, только Shopify-style), придумал текст коммита,
   и даже сам пометил один SHA как `(implied)` (не проверено), но всё
   равно поставил статус `VERIFIED` — прямое нарушение им же принятого
   протокола.

**Вывод: любой результат от Qwen Coder нужно перепроверять так же
строго, как и всё остальное — независимым клоном, а не на слово.**
Пользователь решил на данный момент Qwen не использовать, вернуться к
вопросу позже.

## 7. ВАЖНЫЕ ТЕХНИЧЕСКИЕ ФАКТЫ, НАЙДЕННЫЕ В ПРОЦЕССЕ

- InSales Liquid поддерживает `sort` с параметром свойства:
  `{% assign x = array | sort: 'property' %}` — задокументировано на
  `insales.ru/collection/doc-liquid/product/filtry` и
  `wiki.insales.ru` (фильтр `4.1.6 sort(input, property = z)`). Это
  решило проблему `AggregateOffer`, которую два ИИ независимо оставляли
  нерешённой из-за отсутствия доказательств порядка вариантов.
- `product.available` — задокументированный на `wiki.insales.ru/Objects`
  булев признак наличия товара на уровне товара целиком (не варианта).
- Множественные отдельные `<script type="application/ld+json">` блоки
  для разных типов Schema.org (`Organization` в head.liquid,
  `BreadcrumbList` в layouts.layout.liquid) — это НЕ дубль и не ошибка,
  а стандартная валидная практика. Не нужно консолидировать.
- Паттерн `{% if template contains "X" %}` — уже широко используется в
  `head.liquid` для title/description и теперь также для OG-тегов в
  `layouts.layout.liquid`. Это подтверждённый, работающий способ
  определения типа страницы в этом проекте — можно опираться на него
  для будущих SEO-задач.
