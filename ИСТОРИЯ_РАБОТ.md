# 3. ВАЖНЫЕ УРОКИ

## JS вместо CSS

Category-card инцидент доказал: не лечить CSS/Liquid через JS с `!important`.

## Не путать доказательство и гипотезу

`tag.js`, MutationObserver, изображения, CSS, fonts и third-party должны связываться с конкретным trace/network evidence. Само наличие ресурса ещё не доказывает его причинность.

## Не путать network time и CPU time

`common.v2.27.9.js` может находиться десятки секунд в передаче при плохой сети, не выполняясь десятки секунд на CPU.

## Не смешивать PageSpeed runs

Desktop и mobile, разные throttling conditions и разные запуски нельзя объединять в один «до/после» показатель без явной маркировки.

## Audit discipline

Правильный цикл: **доказательство → маленькая группа изменений → повторный тест → diff → runtime QA**.

# 17. ЗАКОН АРХИТЕКТУРЫ ЗАГРУЗКИ И ПОСТРОЕНИЯ КОДА

## Главный порядок

**Critical Path → First Paint/LCP → Interaction → Analytics/Third-party → Background**

### 1. Critical Path

Сначала загружаются и обрабатываются:

- HTML;
- критический CSS;
- H1 и основной контент первого экрана;
- LCP-элемент;
- минимально необходимая функциональность для отображения и работоспособности страницы.

### 2. First Paint / LCP

LCP должен обнаруживаться максимально рано из первоначального HTML.

Правила:

- LCP не lazy-load;
- LCP должен быть доступен браузеру как можно раньше;
- `fetchpriority` использовать только там, где он действительно повышает приоритет нужного ресурса;
- не создавать LCP-контент только после `DOMContentLoaded`, если этого можно избежать;
- не перегружать critical path большим количеством одновременно высокоприоритетных ресурсов.

### 3. Interaction

После обеспечения первого экрана загружается и выполняется функциональный JavaScript:

- меню;
- корзина;
- compare;
- favorites;
- product controls;
- calculator UI;
- прочие необходимые пользовательские взаимодействия.

**Бизнес-логика калькулятора защищена и в рамках performance-архитектуры не изменяется.**

### 4. Analytics / Third-party

Google Analytics, Яндекс Метрика, GTM, SmartCaptcha и другие third-party-сервисы **не считать критическими зависимостями без доказанной необходимости**.

Они не должны:

- блокировать HTML parser;
- задерживать FCP/LCP;
- конкурировать с критическими ресурсами за сеть;
- создавать ненужную CPU-нагрузку на critical path.

Использовать, где это безопасно:

- `async`;
- `defer`;
- conditional loading;
- lazy initialization;
- запуск после критического отображения.

**Не переносить Метрику вниз механически.** Необходимо сохранить корректность аналитики, одновременно исключив её из критического пути.

### 5. Background

В последнюю очередь или по необходимости выполняются:

- второстепенные виджеты;
- визуальные эффекты;
- некритические изображения;
- фоновые задачи;
- дополнительные сервисы.

### 6. Закон изменений

Каждое performance/refactor-изменение выполняется по цепочке:

**baseline → маленькое изменение → PageSpeed/Trace → Network → Performance → diff → runtime/visual QA → запись результата в `ИСТОРИЯ_РАБОТ.md`**

Массовый refactor запрещён без доказанной причинности.

### 7. Главный принцип

**PageSpeed — это диагностика архитектуры загрузки, а не список отдельных исправлений.**

Приоритет определяется реальным:

**waterfall + trace + runtime behavior**

а не предположением.

SEO, Accessibility и Agentic Browsing нельзя улучшать ценой производительности, и производительность нельзя улучшать ценой этих базовых требований.

**Защищённая бизнес-логика калькулятора и Metal Routing не изменяются в рамках performance-архитектуры.**
